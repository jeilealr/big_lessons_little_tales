# Reusable Feltwillow repository consistency audit prompt

Copy the prompt below into a new agent session from the root of `feltwillow-production`. Replace the bracketed inputs. This is an **audit and report** task; it does not authorize asset generation, deletion, regeneration, rendering, or repository repairs.

---

You are auditing the entire Feltwillow production repository for inconsistencies that could corrupt future image, audio, video, or edit work. Produce a dated, evidence-based report that another agent can use to fix the problems in priority order. Be exhaustive in inventory and dependency checks; distinguish what you actually verified from what you could not inspect.

Inputs:

- Repository root: `[absolute path to feltwillow-production]`
- Execution environment: `[Mac feltwillow Conda / LUMI container / other]`
- Primary production focus: `[story slug, e.g. lion_and_mouse_v6]`; also scan every other story for shared-code or documentation conflicts.
- Report path: `docs/audits/repository-consistency-YYYY-MM-DD.md` (use today's date; add a short suffix if that file already exists).
- User decisions in force: the primary story's own README, visual bible, manifest, approvals, and the latest explicit owner instructions. For `lion_and_mouse_v6`, **keep it fully independent of v5 and every other version**. Do not copy, inherit, reference, render, or use audio, images, clips, approvals, or timing from another Lion and Mouse version. Its current `LUMI_HANDOFF.md` records the intended v6 state. Treat older dated claims in `CLAUDE.md`, root `README.md`, generic rules, and changelogs as claims to test, not permission to override this decision.

## Operating rules

1. Read `CLAUDE.md`, root `README.md`, the primary story's `README.md` and `LUMI_HANDOFF.md` if present, `docs/creation-rules.md`, applicable `.claude/skills/*/SKILL.md`, the story's `visual_bible.json`, `prompt_manifest.json`, `image_approvals.json`, `dialogue_coverage.json`, `timing_plan.json`, `SHOT_PLAN.md`, `TIMING_SHEET.md`, runtime `story.yaml` if present, and relevant code. Discover other files instead of assuming these are exhaustive.
2. Capture the git branch, HEAD commit, dirty status, ignored-file rules, environment, and audit date. Do not mistake a local uncommitted asset for something available after a pull on LUMI. Do not expose credentials, tokens, private audio contents, or unrelated personal files in the report.
3. Use read-only commands and inspections. A checker that writes must use a documented `--check`/dry-run mode or a temporary copy. Do not run image generation, TTS, GPU render, `chain_plan apply`, exports that overwrite files, destructive cleanup, or approvals. The only repository write allowed is the audit report.
4. Cite every material finding with exact repo-relative path and line, manifest record ID, asset path, hash, command result, or visual contact-sheet/frame locator. Quote concise evidence. Mark every conclusion `verified`, `inferred`, or `unverified`. Absence of a file in a Git checkout does not prove it never existed in ignored `work/` or on LUMI.
5. Separate **current state**, **intended state**, **historical experiments**, and **unavailable evidence**. A planned target path, accepted label, generated prompt, successful lint, matching dimensions, or an agent's prior statement does not by itself prove visual quality or owner approval. A candidate is never an approved production input.
6. If evidence conflicts, name both sources, their dates and authority, identify the specific downstream risk, and recommend the smallest resolution. Do not silently choose a value or repair files during this audit.

## Complete inventory and lineage

- Inventory all story slugs and their stage: script, audio, foundations, scene keyframes, approved images, runtime export, rendered clips, take selection, lip-sync, final edit. Give counts and status definitions. Include tracked, untracked, ignored, and missing inputs where the environment permits. Report duplicate/orphaned/superseded files separately from active targets.
- For every active primary-story image record, resolve target, candidate, result, ordered references, reference roles, setup, framing, prompt template, prompt hash, file hash, approval hash, generation provenance, and owner review state. Identify dangling paths, wrong revisions, cross-story/version references, targets that disagree with accepted hashes, stale approvals after any source change, circular dependencies, and references to candidates or deleted assets. Report counts by canonical, expression, pose/reference, plate, prop, sharp scene frame, and blurred portrait.
- Trace every active primary-story dependency from script/audio line to coverage beat, shot, keyframe endpoints, runtime variant, rendered take, selected take, mouth-sync output, and final edit where those stages exist. Identify unmapped narration, duplicate or overlapping coverage, gaps, temporal reversals, impossible state transitions, unused active images, missing endpoint pairs, and clips that cannot be traced back to approved exact image hashes.
- For v6, explicitly search active manifests, bibles, scripts, audio paths, runtime YAML, helper scripts, approvals, and task files for `lion_and_mouse_v5`, `_v4`, `_v3`, `base_story`, `carried_from`, `reuse`, or equivalent implicit imports. A mention in a historical log is documentation history; an active input edge is a blocking defect. Do not suggest restoring an older-version asset as a v6 fix.
- Verify chronological `sNN_CC_...` keyframe names against first use in shot/film order. Check scene number, within-scene counter, shot identity, frame role, revision, duplicate names, filename/path case, and any generated prompt or runtime path. Check video and review clip naming/order separately; do not infer chronology from alphabetical names without comparing the shot plan and coverage.

## Documentation and code authority

- Build a source-of-truth map: which file controls identity, size, plate, prompt, audio timing, approvals, runtime inputs, take selection, and lip-sync. Check whether code actually reads each purported authority, or whether a rule is manual only. Check for alternate writers that overwrite the same file or reintroduce inherited/cross-version values.
- Search current docs, skills, code comments, command examples, and templates for stale paths, deleted tools, obsolete v6 counts/status, old scale targets, old r01 inputs, reuse instructions, or statements that conflict with the current v6 packet. Specifically inspect the top-level `CLAUDE.md` and `README.md`: dated text may still describe the superseded v6 carryover plan. Record the exact passage and the active conflicting evidence. Do not treat historical sections as current policy.
- Check creation and review gates in `production/image_prompts.py`, `image_handoff.py`, `image_approval.py`, `keyframe.py`, `export_runtime.py`, `chain_plan.py`, `chain_preview.py`, `shot.py`, `lip_sync.py`, and `export_handoff.py` as applicable. For each claimed safeguard, state whether it is enforced by code, checked by a command, dependent on manual visual review, or absent. Look for bypasses, stale cache inputs, non-idempotent rebuilds, and approvals that can survive changed references or prompts.
- Check applicable `SKILL.md` files and production guides for contradictory instructions, especially size/ground/contact checks and version separation. Recommend one authoritative wording and links rather than duplicating a changing number in many places.

## Image consistency and physical scene review

- Compare every approved primary-story canonical to its expression, mouth, pose, and prop references. Check head and body proportions; ear/mane/muzzle/eye/nose/teeth design; intrinsic color and felt texture; limb, paw, whisker and tail counts; view-dependent shape; and approval provenance. A file named r02 is not automatically derived from or consistent with the approved r02 canonical. Flag uncertain identity comparisons for owner review with contact-sheet coordinates.
- For each setup, verify the locked v6 plate and its landmarks, crop, camera, light, depth plane, and walkable surface. Compare start/end images and adjacent shots for plate geometry, character scale, head size, position, prop state, lighting, occlusion, and continuous physical action. Detect duplicated candidates, candidate/source copies, stale r01/r02 variants, review outputs mistakenly used as active targets, and keyframes present at both target and `.review/` without clear status.
- Measure screen fractions from actual delivered images, not prompt text alone. In v6 wide/two-character setups, compare Milo's standing ear-to-foot height to the active bible target (0.21 of frame height as of 2026-10-10) and head plus ears (about 0.10); at the same depth compare Milo standing to Leo mane height (about 0.55) and head to Leo face (about 0.42). Re-read the active bible when running this prompt, and report any change to these values. Use each other story's own approved scale rules. Use setup-specific values for seated, portrait, distant, and changed-camera shots. Record measurement method, image size, approximate pixel bounds, depth assumptions, and uncertainty. Do not fail a legitimate close-up by applying a wide-shot target.
- Check that feet/paws actually contact a walkable ground plane, with coherent contact shadow and occlusion. Water, bush crowns, flowers, and floating props are not support. Verify sitting/lying/climbing/jumping and acorn/paw/rope contact causality. For the trapped Leo sequence, verify that the net surrounds his body, every visible rope has a plausible connection, the face remains readable, and the net is not merely a foreground screen. Check close-up exceptions separately.
- Review all available candidate/approved images at full resolution and delivery size if feasible, across every active story. If the collection is too large, first enumerate **all** files and run mechanical checks on **all**; then review a disclosed risk-based sample in each active story plus every owner-flagged image, each canonical, every setup anchor, each start/end pair in a pilot scene, and every obvious outlier. State exact visual coverage and never label unviewed assets visually consistent.

## Audio, timing, video, and edit checks

- Confirm the primary story's script text, dialogue coverage, audio-story slug, scene/line IDs, WAV existence and durations, timing source, and word timings all describe the same version. Check speaker attribution; narrator must not drive a character mouth. Check cuts, holds, first/last frames, cumulative coverage, overlaps/gaps, endpoint chaining, and whether timing is provisional because local audio is absent. Recompute duration/frame-count relationships using the configured frame rate, tolerances, and actual audio where available.
- Verify each runtime shot/variant uses the intended current keyframes and correct closed/open/gnaw mode. Inspect prompt length/truncation, negative prompts that can conjure unwanted objects, shot motion feasibility, seeds, resolution, frame rate, fast setting, task list, and render output naming. Distinguish planned jobs from existing takes. Identify stale frozen keyframes, mismatched hashes, accidental reuse, orphaned take files, and take selection that references a different render revision.
- Where clips exist, inspect metadata and first/middle/last frames, then motion around critical contacts, mouth states, scene cuts, exits, net/rope interactions, and scale drift. Do not conclude motion quality from endpoint stills. Compare selected take, trim, lip-sync product, and final export to the exact source hashes. Note whether LUMI-only files could not be inspected locally.

## Reproducibility and checks

- Verify dependency/environment instructions for Mac `feltwillow` Conda and LUMI container, platform-specific paths, required tools, and whether documented commands run in the available environment. Check Git/LFS/ignore behavior for every required handoff asset, including `.review/`, `work/review/`, v6 audio, generated manifests, and large PNGs. Provide a transfer inventory; never assume Git transports ignored files.
- Run the available non-mutating checks for each active story. For v6, at minimum attempt `python production/image_prompts.py --story lion_and_mouse_v6 build --check`, `... lint`, and `python production/image_handoff.py --story lion_and_mouse_v6 audit`; record exact exit codes and warning counts. Inspect existing tests and run those relevant to changed/current gates if feasible. If a check cannot run, record the missing dependency/input and the command needed on LUMI. Do not call a lint warning harmless without checking its cause.
- Cross-check the report's counts by independent queries where practical. Use hashes for exact identity and image measurements/visual inspection for perceptual identity; neither substitutes for the other.

## Required report structure

Write the report at the requested path with these sections:

1. **Snapshot and scope** — date, environment, branch/commit/dirty state, stories scanned, paths/ignored data available, commands run, visual coverage, and limitations.
2. **Executive decision table** — issue counts by severity: `P0` blocks generation/render/approval or causes cross-version contamination; `P1` likely visible inconsistency or broken handoff; `P2` documentation/automation gap; `P3` cleanup. Separate verified defects from risks and unknowns.
3. **Source-of-truth map** — for each production fact, authoritative file, consuming code, validation gate, and any conflicting document.
4. **Per-story inventory** — stage and count table with accepted/candidate/planned/missing/rendered/selected, plus exact definitions and availability caveats. Keep v5 and v6 in separate rows and separate dependency graphs.
5. **Findings** — one ID per issue (`CONS-001`, ...), severity, status (`verified`/`inferred`/`unverified`), affected story/stage, exact evidence and reproduction, expected versus actual behavior, downstream impact, and smallest recommended fix. Include owner decisions needed only when genuinely ambiguous.
6. **Visual review ledger** — each viewed asset or sheet/frame range, measurements, comparison reference, pass/fail/uncertain, and reviewer confidence. List unviewed files explicitly or link a generated inventory in the same report.
7. **Dependency and stale-data map** — blocked or invalidated images/clips downstream of each changed root, plate, anchor, script/audio line, or approval. Include cross-version edges as blockers for v6.
8. **Remediation sequence** — ordered, bounded tasks with expected validation command and acceptance criterion; place source-of-truth fixes before regenerated derivatives. Distinguish code/doc fixes from images requiring owner visual approval and from LUMI-only checks. Never suggest copying v5 assets into v6.
9. **Command log and unresolved questions** — commands, exit codes, relevant output excerpts, missing evidence, and exact next verification step. The report must stand alone for another agent.

Conclude with a small **go/no-go matrix** for (a) generating new stills, (b) approving stills, (c) exporting a pilot, (d) bulk video rendering, and (e) edit handoff. Each entry must cite its blocking finding IDs or its positive evidence. Do not write “ready” from lint alone. Do not implement fixes in this audit; return the report link and the highest-priority blockers to the owner.
